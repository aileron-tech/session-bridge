# Requirements

- REQ-001: Discover live local Codex and Claude sessions with project and identity.
- REQ-002: Route messages and replies to the specified existing session.
- REQ-003: Preserve pending work and resume routing after service/dependency restarts.
- REQ-004: Preserve native approvals and report held/refused/uncertain delivery honestly.
- REQ-005: Automatically load the bridge for Codex and Claude at startup.
- REQ-006: Validate messages, identities, filesystem and local socket boundaries.
- REQ-007: Expose and message parent sessions only; subagents remain managed by their parents.
- REQ-008: Filter session discovery and recipient delivery by an optional exact project name or absolute directory path, including pending retries.
- REQ-009: Advertise parent Codex sessions as native Claude-compatible peers with accurate process identity and route native messages to their existing Codex queues.
- REQ-010: Connect persistently to the local Codex App Server, discover loaded parent threads, consume live status events, reload MCP, and route durable messages without launching duplicate sessions; reconnect after dependency restart.
- REQ-011: Reuse a running Codex App Server. When absent, host it inside the bridge by default; --codex-app-server instead starts the external native daemon. Persist the selected mode when installing the background bridge.
- REQ-012: Reference Codex through a pinned GitHub submodule under vendor/codex; link only required runtime/helper modules and their dependencies, without paths to an external source checkout.
- REQ-013: A single bridge executable also dispatches the code-mode, plugin, execution and patch helper roles required by embedded Codex.
- REQ-014: MCP listing and sending default to the caller's exact working directory; CLI listing defaults to its current directory. Other projects require an explicit project filter. Persist the resolved send scope for retries.

- REQ-015: The bridge provides messaging only. It never embeds, starts or configures Codex App Server; model catalogs and runtimes remain owned by native clients. Discover live sessions from process-owned metadata and deliver through native `codex queue` without `--resume` or model overrides; a hung `codex queue` ends after 20 seconds as `uncertain`. When a live (loaded) thread keeps a message from the user (admin page, channel post, schedule) in its queue while idle, including after the user interrupted it, the bridge asks the user's Codex app server (its control socket) to start exactly that queued item by its id (`thread/queue/start`, right after queueing and every 30 seconds while it waits), as Codex does on idle; never for an agent's message, never another queued item, never for an unloaded thread or a paired laptop's thread, never a resume or a headless run; native approval checks stay in Codex. When Codex refuses because a turn is running and the user's post has waited at least 2 minutes since the bridge took it, the bridge hands that post to the running turn as the user's own mid-turn input (`turn/steer` with the running turn's id, as the TUI sends text typed during a turn), then removes it from Codex's queue (`thread/queue/delete`); each post at most once, never into a review or compact turn (Codex refuses). A hand-over is recorded in `steered.json` before it is sent and kept across restarts: one whose outcome is uncertain is never sent again nor removed, and when the turn took the post but Codex kept it queued, only the removal is retried. Before starting or handing over anything, older copies of a scheduled post (same text, same thread) still in Codex's queue behind a newer copy are removed from it (`thread/queue/delete`), so only the newest copy runs; posts the user typed and agents' posts are never removed. Preserve durable delivery semantics. Supersedes the App Server and helper requirements REQ-010 through REQ-013.

- REQ-016: Run the messaging service, CLI, MCP server and durable store on Windows as well as macOS. The control endpoint is a named pipe that only the current user can open, and a client rejects a pipe served by another user. Installation registers a per-user logon task that starts the service at logon and restarts it after failure, without elevation. Native session discovery and delivery on Windows are not part of this requirement.

- REQ-017: When the user turns networking on, the bridge announces itself and finds other bridges on the local network with Zeroconf (mDNS + DNS-SD, IPv4). Two bridges exchange sessions and messages only after the user pairs them: the user picks a discovered laptop, that laptop shows a one-time 6-digit code (desktop notification, `session-bridge pair`, admin page), and the user types it on the first laptop. The code is valid 2 minutes, allows 3 tries, and is verified with SPAKE2 bound to both bridges' keys; paired bridges then authenticate each other with pinned Noise keys on every connection. Networking is off by default, announcements carry only a protocol version and key fingerprint, and agents cannot pair. Sessions on a paired laptop appear in listings with their host; a message to one is forwarded to that laptop's bridge, which owns its delivery and reports its state back. Durable delivery rules apply across laptops: an interrupted forward is uncertain and never resent automatically.

- REQ-018: `session-bridge admin` opens a local setup page served by the bridge on 127.0.0.1 only. It shows this bridge's network state, discovered and paired laptops, incoming pairing codes and recent deliveries, and offers network on/off, pair, enter code and unpair. Every API call needs the per-service token from the command's URL and the page's own Host and Origin. Since REQ-019 the page also lists sessions and carries the user's messages; agent sends and native peer frames are not available there.

- REQ-019: On the admin page the user lists live sessions on this laptop and on paired laptops, writes to a session, and reads recent messages with their text formatted from Markdown. Message text is converted to typed blocks and rendered as text only: raw HTML is never markup and only http, https and mailto links keep a target. A message from the user carries a per-laptop `user:<uuid>` address, says it was written by the user through the admin page, and never counts as approval for an action that needs permission; native approval checks stay. Agents answer that address with `send_message`; the answer is `delivered` to the page, also across paired laptops. Only the admin page writes as the user: the control socket refuses it and no agent send may name the user as its sender. This keeps agents' tools (CLI, MCP) from writing as the user by mistake; it is not a security boundary, because any program of the same account can open the admin page (`session-bridge admin` returns its URL and token). That is why a user message never carries approval.

- REQ-020: On the admin page every project with live sessions is a channel (`#project`) spanning this laptop and paired laptops; the page shows conversations like a chat (channels, direct messages, read-only conversations between agents). A channel post reaches the sessions it mentions: `@channel` every session of the project, `@name` one session by name; a post without a mention, or naming an unknown or ambiguous session, is refused. The post carries a per-channel user address, so answers to it appear in the channel. Channel posts follow REQ-019: the user's words, never an approval, sent from the admin page only.

- REQ-021: The bridge runs without the background service: `session-bridge daemon` serves from a shell on macOS and Windows until stopped, and `SESSION_BRIDGE_STATE` (an absolute directory) gives it a state directory, control endpoint, admin page and messages of its own beside the installed service. With that variable, a client that finds no bridge fails at once with a hint instead of starting the installed service. `session-bridge uninstall` removes only the background service registered for this home (LaunchAgent or logon task) and stops it; the executable, MCP entries and state stay, and a service registered for another home is left alone.

- REQ-022: On macOS the bridge started by its LaunchAgent (or from a shell with `SESSION_BRIDGE_TRAY=1`) shows a menu-bar icon that lives as long as the bridge. Its menu shows the version, state, session count, networking and whether the service or a shell runs it, and offers Open admin, Install service (a bridge from a shell on the default state) or Uninstall service in a Background service submenu, and Shut down; uninstall and shut down ask for confirmation first. `session-bridge stop` stops this home's bridge: the installed service through its supervisor (until next login), otherwise with a shutdown request on the control socket, which the admin page cannot send. Install and uninstall never replace or remove a service registered for another home; a bridge on its own state directory offers neither.

- REQ-023: Each published GitHub release carries prebuilt binaries for macOS (arm64, x86_64) and Windows (x86_64) and a SHA256SUMS file, built by the release workflow. `session-bridge update --check` reports whether a newer release exists; `session-bridge update` downloads this platform's binary, refuses it unless its SHA-256 matches SHA256SUMS, and installs it: through the new version's `install` (service restarted) when this home's service is installed, otherwise by replacing the executable in `~/.local/bin`. The menu-bar icon offers the same check and update on request; nothing contacts GitHub unless asked.

- REQ-024: On the admin page the user sets or clears a channel's default recipient (a session of the project, kept by name in `channels.json` across restarts). A channel post without a mention goes to it; any mention overrides it; a default that is not live is refused with a message. Only the admin page changes it. The sidebar groups channels and direct messages by project, and conversations between agents by the agent that started them.

- REQ-025: On the admin page the user schedules channel posts with cron expressions: each schedule (cron, project channel, recipient: a session name, `@channel`, or the channel default and the message's mentions; message) is kept in `schedules.json` and installed as one managed line in the user's crontab that runs `session-bridge scheduled <id>`. The page shows the user's other crontab lines read-only and never rewrites them; only the admin page adds, edits or deletes schedules. A run posts the message as the user's post in the channel, marked scheduled, never an approval; a run while the bridge is down is not sent later. A run never stacks posts: when the schedule's previous post to a recipient is still unread (pending or held in the bridge, or a Codex post on this laptop still in Codex's queue; Claude sends no receipt, so its queued posts count as read), that recipient is skipped, and the run's output and the Cron tab say the previous post was not processed and sending was skipped. The Cron tab shows each schedule's last run. Windows has no crontab, so scheduling is unavailable there.

- REQ-026: On the admin page's Roles tab the user keeps roles (a name and instructions, kept as files: REQ-037) and assigns them to sessions by name. The roles master (multi-agent orchestration and kickoff) and researcher (critical-path research) are offered once, with the user's texts; a role of that name the user already has is kept, and a deleted one is not offered again. Assigning sends the instructions to the session once, as the user's message (never an approval), and shows the role as a badge; in a channel, `@role` reaches every session holding it (a session's own name wins over a role of the same name), and a role can be a channel's default recipient. Renaming a role keeps its assignments; deleting it removes them. Only the admin page changes roles. The page is organized in tabs (Chats, Cron, Peers, Roles); every session shows its peer (laptop) as a badge, and the chat sidebar groups by peer or project, filters by peer and sorts by recent activity or name.

- REQ-027: A bridge outside the local network is reached through SSH, not a public port: on the remote host the bridge runs with `network on --local-only` (listens on 127.0.0.1, no announcement); `session-bridge remote add <ssh-host> [--port <n>]` (or the Peers tab) makes this bridge keep one `ssh -N` connection to that host with the user's own SSH configuration, keys or agent (BatchMode, no prompts), forwarding a local port to the remote bridge and a port on the remote's loopback back to this one, and reconnecting when it drops. `pair <ssh-host>` pairs through the tunnel with the remote's one-time code; afterwards both directions use the pinned Noise channel inside SSH. Remote hosts are listed with their tunnel state and removed with `remote remove`.

- REQ-028: The user starts a Claude or Codex session with a role (admin page channel, `session-bridge spawn`): it is named `{short}-{role}-{n}` (short project name set per project in `spawn.json`, default the folder name; lowest free n among live and starting sessions), starts in the project's directory with the role's instructions as its first prompt and the role assigned, and keeps the native approval checks, unless the user chose other approvals for sessions they start themselves (REQ-034); a session an agent starts always asks. A spawn service per system opens it: iTerm2 (a new tab in its front window; the default when it is installed and the user chose no terminal) or Terminal (macOS), `cmd` (Windows), tmux, screen or a detached `script` (Linux); the window runs only `session-bridge launch <token>`, which claims its directory, name and prompt from the bridge and becomes the agent, so no user text enters a shell or AppleScript command. Codex sessions get their name through the launched process id (kept by session id in `names.json`). The user closes a local session (its process gets SIGTERM; a process that carries several sessions or a Codex app server is refused). The built-in role `root` cannot be renamed or deleted; root's authority belongs to the session the user gave it (by session id) or the session started as root (bound through its launch: only the launch process itself may claim it: the connecting process by the control socket's peer credentials, running exactly `<executable> launch <token> [<state>]` (not checked on Windows, which gives no peer process); the launched process itself takes the name whenever it appears, a session under it only within 2 minutes of the claim), not to whichever session has the name, and only a session that really holds root is protected from root's close; a session holding it may, through MCP, start sessions with any other role in its own project (its directory; below 8 live sessions) and close non-root sessions there; no session can start or close a root session. The admin page acts only as the user. The kickoff template fills a request for issue status and queued work in a direct conversation.

- REQ-029: The admin page's Peers tab (and nowhere else on the page) shows usage, refreshed about every 5 seconds while it is visible: for this laptop and each paired bridge, CPU %, memory used and total, and disk used and total of the filesystem that holds the user's home; for each live session on this laptop, the CPU % and memory of its process tree (the process and its descendants). A process that carries several sessions (a shared Codex app server, `codex --remote`) is shown as shared with its own numbers only, never summed or split per session. Sizes are binary units named as such (GiB). Usage polls read the last discovered sessions and never run discovery; a local sample serves every reader for 2 seconds, and a paired bridge's answer for 30 seconds, with longer waits (up to 5 minutes) after failures. A peer's usage request that fails gets a fixed text; the detail stays in the local log. A bridge asks each paired bridge for its usage over the paired channel; a bridge that does not answer, or an older one that does not know the request, is shown as "usage unavailable", never as an error.

- REQ-030: The admin page's Projects tab lists this laptop's projects (directories with live sessions, and remembered ones, REQ-038; paired laptops' sessions are not shown or changed there) with their sessions, roles and master. The user starts a session with a role in a project and closes one there (REQ-028 rules). Each project has a master: the session the user chose (kept by name in `channels.json`, admin page only), else the session named or holding the role `master`, else `lead`, else the first by name. The tab and the waiting view (REQ-032) use the sessions the bridge last discovered; polling them runs no discovery in the bridge's message loop. The chat sidebar groups by project and sorts by name by default.

- REQ-031: A kickoff carries the team table: a Markdown table after the text, under a line saying the bridge generated it from session data (not the user's words), built at send time, of every session in the recipient's project on this laptop and paired laptops, with its role, agent, host, state, CPU and memory (sessions on this laptop) and when it last sent or received a message (never the message text). A schedule carries it when its "Attach the team table" option is on (on for saved schedules whose message says "kick off"); the admin page's Kickoff button makes the next direct message carry it. The message with its table stays within the message size limit; rows that do not fit are counted.

- REQ-032: The bridge reads, never changes, Codex's own queue (`queue_<n>.sqlite`, `queued_items`) to see which messages wait for a Codex thread, matching the bridge's messages by their `Message ID` line. A bridge message to a live local Codex session that is `queued` and no longer in that session's queue was taken by the session and becomes `delivered`. The admin page shows, per local session, what waits unread: messages the bridge has not handed over (pending, held) and bridge messages still in Codex's queue, as a count in the sidebar and header, the list in the session's header, and a warning with the count above the message box (also in a channel, per member) before the user sends.

- REQ-033: Session discovery never runs in the bridge's message loop: a background task discovers every 3 seconds and hands the loop its result; a request names an unknown session before the loop discovers at once. The costly Codex scan (`lsof`) runs only when Codex's processes or thread lock files changed, and at least every 30 seconds; between scans the last Codex sessions are kept while their process lives. The MCP server forwards the bridge's replies as JSON without reading them into its own version's types, so a session's long-running MCP server keeps working after the bridge is updated. A started session's terminal and agent never get the bridge service's own environment (`CLAUDE_CONFIG_DIR`, `CODEX_HOME` at their defaults, the service's settings).

- REQ-034: The admin page's Run tab sets how sessions the user starts from the admin page run: the terminal app (Terminal or iTerm2), and per agent an approvals choice (Claude: ask, accept edits, auto, don't ask, plan, bypass; Codex: ask, on request, auto review, never ask in a workspace sandbox, bypass) and extra flags, kept in `spawn.json`; the user can fill them from their zsh `claude` and `codex` aliases on request (ImportAliases, admin page only). Sessions started any other way (a root agent, the CLI or the control socket, which any program of the account can use) always ask and get no extra flags or user instructions. Extra flags are an allowlist of known flags with their arity (values attached with `=` or the next word; no `--`, subcommands or prompts; Codex `-c` overrides may not touch `mcp_servers`); flags the bridge sets are refused with the reason. The bridge always sets Claude's name (`-n`), its first prompt and `--disallowedTools AskUserQuestion`, and Codex's first prompt plus `--remote unix://` when the user's Codex app server is running. The first prompt carries the role's instructions, the user's own instructions (admin page only), and tells the session not to ask interactive questions but to send decisions to the project's master the user chose (bound to that session), or else to the user in the project's channel.

- REQ-035: On the admin page the user removes a bridge message that still waits for a session: one the bridge has not handed over (pending, held) is marked refused ("removed by the user") and never retried; one in a Codex thread's own queue is first taken out of that queue through the user's Codex app server (thread/queue/delete), then marked the same way. Only bridge messages, only from the admin page; a message already read or delivered cannot be removed.

- REQ-036: When the user turns on "Phone access" on the admin page (off by default; only the admin page turns it on, pairs and unpairs phones, never the control socket or a phone), the bridge serves a phone admin app over HTTPS (TLS 1.3, port 47821) to private IPv4 addresses on a local subnet only, reached by the laptop's LAN IP address (the default route's first; every private address is offered), under a per-bridge P-256 root that the phone trusts once (an iOS profile or the root itself over plain HTTP on the next port, checked against the fingerprint the admin page shows). The root is name-constrained to the private IPv4 ranges and the bridge's `sb-<label>.local` name; the server certificate it issues names the current LAN addresses and is issued again when they change, so a new address needs no new profile. The bridge also announces `sb-<label>.local` over mDNS independent of laptop networking, as an extra name that is never required. The user pairs a phone with a one-time code (80 bits, shown as `ABCD-EFGH-JKLM-NPQR` and in a QR code, valid 120 s, one guess) and accepts the phone's key on the laptop; a desktop notification shows each pairing; at most 5 phones. Every call is authenticated by that phone's pinned key through sessions opened by signing a one-time challenge (15 min idle, 12 h at most), and is rate limited. A paired phone lists sessions, reads and sends chat and channel messages, and edits schedules and roles; it cannot send as an agent or a schedule, give, change or delete the root role, change networking, pairing, remote hosts, run settings, approvals or phones, read the user's other crontab lines or local session and project directories, or start or close sessions; a connection idle for 60 s is closed. Phone messages are the user's words, never approval (REQ-019). A send carrying a `client_id` (phone, kept per device, or admin page) repeated within 10 minutes gets the first answer and is never sent twice, and the same id with a different request is refused; nothing is resent automatically. Unpairing or turning phone access off ends the phone's sessions at once. Phone access is available on macOS and Linux; on Windows it reports that it is not available.

- REQ-037: Each role is a Markdown file `<name>.md` in the roles folder (`roles/` in the state directory, private to the user, files written atomically and readable by the user only); the file name is the role name and the file holds the instructions as they are. `roles.json` keeps only the assignments, the root sessions and the presets offered; roles it still holds are written to files on start, never replacing a file. The bridge lists the folder every 2 s off the event loop and reads only the files whose listing changed: a new file is a new role, a deleted file a deleted role (its assignments stay), an edited file new instructions, which are not sent to the sessions holding the role. A file that is not a role (an invalid name, empty, over 16000 bytes, containing NUL, not UTF-8, not a regular file, a symbolic link, or a second file for one name) is not loaded, logged once per change and listed on the Roles tab with the reason; links are never followed; hidden and non-`.md` files are ignored. A missing `root.md` is written again with the built-in instructions; one that is not loaded is kept as it is while the built-in instructions apply. Roles are ordered by name, root last. A save from the admin page or the phone over a role file that exists must carry the version of the file it edited; without it, or when the file changed on disk since, it is refused (HTTP 409) and the file is left unchanged. A new role needs no version. Only the admin page opens the roles folder in the file manager.

- REQ-038: A local session that is no longer live (not in the bridge's last discovery: closed, exited, or its id replaced) has ended. A message for it that waits (pending) or is sent to it is refused ("<name> has ended; not delivered") and never delivered if the session id returns; a paired laptop's bridge does the same for its own sessions and reports the refusal back, while a message for an away paired laptop stays pending (REQ-003). On the admin page, Chats lists direct conversations only with live sessions (and user addresses) and conversations between agents only when both are live; a project's channel is listed only while the project has a live session; a selected conversation that is no longer listed is closed. Messages stay in the store. The Projects tab keeps every local project directory the bridge has known a session in (`sessions.json`), listed with no sessions when none is live, while the folder exists and is not under a system temp folder (`/tmp`, `/private/tmp`, `/var/folders`, the OS temp folder) outside the bridge's home.
