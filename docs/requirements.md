# Requirements

- REQ-001: Discover live local Codex and Claude sessions with project and identity.
- REQ-002: Route messages and replies to the specified existing session.
- REQ-003: Preserve pending work and resume routing after service/dependency restarts.
- REQ-004: Preserve native approvals and report held/refused/uncertain delivery honestly.
- REQ-005: Automatically load the bridge for Codex and Claude at startup.
- REQ-006: Validate messages, identities, filesystem and local socket boundaries.
- REQ-007: Expose and message parent sessions only; subagents remain managed by their parents.
- REQ-008: Filter session discovery and recipient delivery by an optional exact project name or absolute directory path, including pending retries.
- REQ-009: Advertise parent Codex sessions as native Claude-compatible peers with accurate process identity and route native messages to their existing Codex queues.
- REQ-010: Connect persistently to the local Codex App Server, discover loaded parent threads, consume live status events, reload MCP, and route durable messages without launching duplicate sessions; reconnect after dependency restart.
- REQ-011: Reuse a running Codex App Server. When absent, host it inside the bridge by default; --codex-app-server instead starts the external native daemon. Persist the selected mode when installing the background bridge.
- REQ-012: Reference Codex through a pinned GitHub submodule under vendor/codex; link only required runtime/helper modules and their dependencies, without paths to an external source checkout.
- REQ-013: A single bridge executable also dispatches the code-mode, plugin, execution and patch helper roles required by embedded Codex.
- REQ-014: MCP listing and sending default to the caller's exact working directory; CLI listing defaults to its current directory. Other projects require an explicit project filter. Persist the resolved send scope for retries.

- REQ-015: The bridge provides messaging only. It never embeds, starts, configures, or connects to Codex App Server; model catalogs and runtimes remain owned by native clients. Discover live sessions from process-owned metadata and deliver through native `codex queue` without `--resume` or model overrides. The native CLI owns any runtime connection. Preserve durable delivery semantics. Supersedes the App Server and helper requirements REQ-010 through REQ-013.

- REQ-016: Run the messaging service, CLI, MCP server and durable store on Windows as well as macOS. The control endpoint is a named pipe that only the current user can open, and a client rejects a pipe served by another user. Installation registers a per-user logon task that starts the service at logon and restarts it after failure, without elevation. Native session discovery and delivery on Windows are not part of this requirement.

- REQ-017: When the user turns networking on, the bridge announces itself and finds other bridges on the local network with Zeroconf (mDNS + DNS-SD, IPv4). Two bridges exchange sessions and messages only after the user pairs them: the user picks a discovered laptop, that laptop shows a one-time 6-digit code (desktop notification, `session-bridge pair`, admin page), and the user types it on the first laptop. The code is valid 2 minutes, allows 3 tries, and is verified with SPAKE2 bound to both bridges' keys; paired bridges then authenticate each other with pinned Noise keys on every connection. Networking is off by default, announcements carry only a protocol version and key fingerprint, and agents cannot pair. Sessions on a paired laptop appear in listings with their host; a message to one is forwarded to that laptop's bridge, which owns its delivery and reports its state back. Durable delivery rules apply across laptops: an interrupted forward is uncertain and never resent automatically.

- REQ-018: `session-bridge admin` opens a local setup page served by the bridge on 127.0.0.1 only. It shows this bridge's network state, discovered and paired laptops, incoming pairing codes and recent deliveries, and offers network on/off, pair, enter code and unpair. Every API call needs the per-service token from the command's URL and the page's own Host and Origin. Since REQ-019 the page also lists sessions and carries the user's messages; agent sends and native peer frames are not available there.

- REQ-019: On the admin page the user lists live sessions on this laptop and on paired laptops, writes to a session, and reads recent messages with their text formatted from Markdown. Message text is converted to typed blocks and rendered as text only: raw HTML is never markup and only http, https and mailto links keep a target. A message from the user carries a per-laptop `user:<uuid>` address, says it was written by the user through the admin page, and never counts as approval for an action that needs permission; native approval checks stay. Agents answer that address with `send_message`; the answer is `delivered` to the page, also across paired laptops. Only the admin page writes as the user: the control socket refuses it and no agent send may name the user as its sender. This keeps agents' tools (CLI, MCP) from writing as the user by mistake; it is not a security boundary, because any program of the same account can open the admin page (`session-bridge admin` returns its URL and token). That is why a user message never carries approval.

- REQ-020: On the admin page every project with live sessions is a channel (`#project`) spanning this laptop and paired laptops; the page shows conversations like a chat (channels, direct messages, read-only conversations between agents). A channel post reaches the sessions it mentions: `@channel` every session of the project, `@name` one session by name; a post without a mention, or naming an unknown or ambiguous session, is refused. The post carries a per-channel user address, so answers to it appear in the channel. Channel posts follow REQ-019: the user's words, never an approval, sent from the admin page only.

- REQ-021: The bridge runs without the background service: `session-bridge daemon` serves from a shell on macOS and Windows until stopped, and `SESSION_BRIDGE_STATE` (an absolute directory) gives it a state directory, control endpoint, admin page and messages of its own beside the installed service. With that variable, a client that finds no bridge fails at once with a hint instead of starting the installed service. `session-bridge uninstall` removes only the background service registered for this home (LaunchAgent or logon task) and stops it; the executable, MCP entries and state stay, and a service registered for another home is left alone.

- REQ-022: On macOS the bridge started by its LaunchAgent (or from a shell with `SESSION_BRIDGE_TRAY=1`) shows a menu-bar icon that lives as long as the bridge. Its menu shows the version, state, session count, networking and whether the service or a shell runs it, and offers Open admin, Install service (a bridge from a shell on the default state) or Uninstall service in a Background service submenu, and Shut down; uninstall and shut down ask for confirmation first. `session-bridge stop` stops this home's bridge: the installed service through its supervisor (until next login), otherwise with a shutdown request on the control socket, which the admin page cannot send. Install and uninstall never replace or remove a service registered for another home; a bridge on its own state directory offers neither.

- REQ-023: Each published GitHub release carries prebuilt binaries for macOS (arm64, x86_64) and Windows (x86_64) and a SHA256SUMS file, built by the release workflow. `session-bridge update --check` reports whether a newer release exists; `session-bridge update` downloads this platform's binary, refuses it unless its SHA-256 matches SHA256SUMS, and installs it: through the new version's `install` (service restarted) when this home's service is installed, otherwise by replacing the executable in `~/.local/bin`. The menu-bar icon offers the same check and update on request; nothing contacts GitHub unless asked.

- REQ-024: On the admin page the user sets or clears a channel's default recipient (a session of the project, kept by name in `channels.json` across restarts). A channel post without a mention goes to it; any mention overrides it; a default that is not live is refused with a message. Only the admin page changes it. The sidebar groups channels and direct messages by project, and conversations between agents by the agent that started them.

- REQ-025: On the admin page the user schedules channel posts with cron expressions: each schedule (cron, project channel, recipient: a session name, `@channel`, or the channel default and the message's mentions; message) is kept in `schedules.json` and installed as one managed line in the user's crontab that runs `session-bridge scheduled <id>`. The page shows the user's other crontab lines read-only and never rewrites them; only the admin page adds, edits or deletes schedules. A run posts the message as the user's post in the channel, marked scheduled, never an approval; a run while the bridge is down is not sent later. Windows has no crontab, so scheduling is unavailable there.

- REQ-026: On the admin page's Roles tab the user keeps roles (a name and instructions, in `roles.json`) and assigns them to sessions by name. Assigning sends the instructions to the session once, as the user's message (never an approval), and shows the role as a badge; in a channel, `@role` reaches every session holding it (a session's own name wins over a role of the same name), and a role can be a channel's default recipient. Renaming a role keeps its assignments; deleting it removes them. Only the admin page changes roles. The page is organized in tabs (Chats, Cron, Peers, Roles); every session shows its peer (laptop) as a badge, and the chat sidebar groups by peer or project, filters by peer and sorts by recent activity or name.

- REQ-027: A bridge outside the local network is reached through SSH, not a public port: on the remote host the bridge runs with `network on --local-only` (listens on 127.0.0.1, no announcement); `session-bridge remote add <ssh-host> [--port <n>]` (or the Peers tab) makes this bridge keep one `ssh -N` connection to that host with the user's own SSH configuration, keys or agent (BatchMode, no prompts), forwarding a local port to the remote bridge and a port on the remote's loopback back to this one, and reconnecting when it drops. `pair <ssh-host>` pairs through the tunnel with the remote's one-time code; afterwards both directions use the pinned Noise channel inside SSH. Remote hosts are listed with their tunnel state and removed with `remote remove`.

- REQ-028: The user starts a Claude or Codex session with a role (admin page channel, `session-bridge spawn`): it is named `{short}-{role}-{n}` (short project name set per project in `spawn.json`, default the folder name; lowest free n among live and starting sessions), starts in the project's directory with the role's instructions as its first prompt and the role assigned, and keeps the native approval checks (plain `claude`/`codex`, no permission flags). A spawn service per system opens it: Terminal or iTerm2 (macOS), `cmd` (Windows), tmux, screen or a detached `script` (Linux); the window runs only `session-bridge launch <token>`, which claims its directory, name and prompt from the bridge and becomes the agent, so no user text enters a shell or AppleScript command. Codex sessions get their name through the launched process id (kept by session id in `names.json`). The user closes a local session (its process gets SIGTERM; a process that carries several sessions or a Codex app server is refused). The built-in role `root` cannot be renamed or deleted; root's authority belongs to the session the user gave it (by session id) or the session started as root (bound through its launch: only the launch process itself may claim it, and only a session that appears within 2 minutes of the claim takes the name), not to whichever session has the name, and only a session that really holds root is protected from root's close; a session holding it may, through MCP, start sessions with any other role in its own project (its directory; below 8 live sessions) and close non-root sessions there; no session can start or close a root session. The admin page acts only as the user. The kickoff template fills a request for issue status and queued work in a direct conversation.

- REQ-029: The admin page's Peers tab (and nowhere else on the page) shows usage, refreshed about every 5 seconds while it is visible: for this laptop and each paired bridge, CPU %, memory used and total, and disk used and total of the filesystem that holds the user's home; for each live session on this laptop, the CPU % and memory of its process tree (the process and its descendants). A process that carries several sessions (a shared Codex app server, `codex --remote`) is shown as shared with its own numbers only, never summed or split per session. Sizes are binary units named as such (GiB). Usage polls read the last discovered sessions and never run discovery; a local sample serves every reader for 2 seconds, and a paired bridge's answer for 30 seconds, with longer waits (up to 5 minutes) after failures. A peer's usage request that fails gets a fixed text; the detail stays in the local log. A bridge asks each paired bridge for its usage over the paired channel; a bridge that does not answer, or an older one that does not know the request, is shown as "usage unavailable", never as an error.
